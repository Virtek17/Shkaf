# Состояние аренды и точки подключения сервера

## Переходы

| Состояние | Событие | Результат / ограничение |
| --- | --- | --- |
| Нет сессии | START | checking; обязательно согласие, корректный срок и отсутствие другой незавершённой аренды товара |
| checking | AVAILABILITY_CONFIRMED | payment с абсолютным expiresAt либо unavailable |
| checking | AVAILABILITY_FAILED | unavailable с сообщением об ошибке проверки и повторной попыткой |
| payment / payment-error | PAYMENT_REQUESTED | paying; второе нажатие игнорируется |
| paying | PAYMENT_CONFIRMED / PAYMENT_FAILED | pickup / payment-error |
| payment-error | PAYMENT_RETRY | payment, срок брони не продлевается |
| pickup / locker-error | LOCKER_OPEN_REQUESTED | opening |
| opening | LOCKER_OPENED / LOCKER_OPEN_FAILED | kit / locker-error |
| kit | KIT_TOGGLED | Изменение одного корректного индекса комплекта |
| kit | KIT_CONFIRMED | active только при подтверждении всех позиций; startedAt обязателен |
| pickup / opening / locker-error / kit | PROBLEM_OPENED | problem с сохранением места возврата |
| problem | PROBLEM_CHANGED | Изменение причины / описания; описание до 1000 символов |
| problem | PROBLEM_PREPARED | problem-sent; это подготовка, отправки нет |
| problem-sent | PROBLEM_EDITED | problem |
| problem | PROBLEM_CLOSED | pickup либо kit, согласно сохранённому месту возврата |
| Любое состояние с expiresAt | EXPIRE либо пользовательское / серверное событие после срока | expired |
| expired / unavailable | RECHECK | checking, если нет другой действующей сессии этого товара |
| active | События предыдущих этапов | Игнорируются; возврат вещи ещё не реализован |

Недопустимое событие оставляет тот же объект состояния. Ответ операции дополнительно проверяет `revision`: результат старой попытки не применяется к новой. При каждом переходе revision увеличивается. Проверка срока идёт перед обработкой результата.

Единственный источник решения об истечении — чистая модель. Провайдер вызывает EXPIRE раз в секунду и при AppState active. Экран обновляет только показания таймера. В текущем сценарии бронь перестаёт отсчитываться при переходе к проверке комплекта, как и до рефакторинга. При обращении в поддержку из pickup срок продолжает действовать, чтобы форма не позволяла обойти истечение.

Это локальные правила прототипа. Срок 10 минут, результаты оплаты и открытие замка имитируются. Перед реальной интеграцией нужно согласовать серверные состояния, в том числе обработку оплаты, подтверждённой после истечения локального таймера. Такой платёж нельзя игнорировать или повторять без сверки с сервером.

## Идентификаторы и снимок условий

- `productId` — прежний публичный UUID товара.
- `displayCode` — код для дизайна, не ключ доступа.
- `rentalId` — отдельный идентификатор сессии. Сейчас локальный `demo-...`, в реальном API выдаётся сервером.
- `/rental-flow/[id]` по-прежнему принимает productId. Новые переходы добавляют query `rentalId` для точного выбора сессии.
- Старая ссылка без query открывает последнюю сессию данного товара. Неверная комбинация идентификаторов показывает «Аренда не найдена».
- После неудачной или истёкшей сессии можно создать новую, сохранив старую в состоянии. Одновременные действующие аренды одного товара блокируются локально; сервер обязан отдельно проверять доступность.

В сессии хранится копия товара, стоимости и срока, а вложенные комплект, пункт выдачи, состояние и пометки копируются. Изменение каталога не меняет согласованные данные сессии.

## Демо

`shared/config/environment.ts` явно объявляет текущий прототип демо. Меню инструментов доступно только при `__DEV__`; оно создаёт изолированный снимок `preview`. Управление этим снимком не попадает в рабочий Context. Чтобы вернуться к рабочему процессу, нажать «Вернуться к аренде».

Рабочие операции продолжаются в провайдере после ухода с экрана. Выбранные состояния ожидания в предпросмотре стоят на паузе до «Продолжить сценарий». Постоянное хранение выключено. После перезапуска приложения сессии сбрасываются.

## Восстановление и сервер: отдельная задача

Постоянное хранение в этот рефакторинг не добавлено. Для следующего этапа:

1. Утвердить контракт сервера, авторизацию и состояния операций.
2. Хранить локально только допустимый минимум: rentalId, productId, версию формата и несекретный черновик. Не хранить платёжные реквизиты.
3. После запуска валидировать и мигрировать версию локальных данных. Повреждённые данные не должны ломать приложение.
4. По rentalId запросить авторизованное серверное состояние. До сверки не объявлять оплату и выдачу подтверждёнными.
5. Сверить время с сервером, обработать офлайн и истёкшую бронь.
6. Использовать согласованный серверный ключ идемпотентности для платежа и команды замку; локальная защита от двойного нажатия этого не заменяет.
7. Обработать завершение операции после отмены клиента, сетевого таймаута или повторного запуска.

Интерфейсы адаптеров находятся в `features/rentals/api` и `entities/product/api`. Настоящие эндпоинты и DTO не выдуманы.
