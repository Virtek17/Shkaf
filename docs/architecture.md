## Границы модулей

`app/core → features → entities → shared`. Функциональные модули могут обращаться к публичному интерфейсу другого модуля, если это необходимо: каталог использует публичные варианты срока аренды. Общие сущности не зависят от экранов. Нельзя импортировать внутренний файл чужого модуля вместо его `index.ts`.

Внутри одного модуля использовать относительные импорты. Публичный `index.ts` предназначен для внешних потребителей; импорт собственного barrel-файла внутри модуля может создать цикл.

ESLint проверяет направление зависимостей и публичные границы. `npm run check:architecture` проверяет циклы статических runtime-импортов TypeScript. Типовые зависимости исключены из проверки циклов. Нативное и web-разрешение файлов дополнительно проверяется экспортом Expo; скрипт не заменяет сборщик.

Чистая модель аренды не использует React, Expo Router, HTTP или компоненты. Провайдер — адаптер React в той же папке с явным исключением из правила линтера.

## Добавить экран

1. Создать экран в соответствующем `features/<module>/screens/`.
2. Экспортировать его через публичный `index.ts`.
3. Добавить тонкий файл в `src/app/`, который экспортирует экран.
4. Для отдельного экрана использовать `ScreenFrame`. Вкладки уже обёрнуты им в `AppTabs`: второй каркас там не нужен.
5. Выбрать обычную разметку, ScrollView или FlatList. Каркас не добавляет прокрутку автоматически.

Верхней safe area владеет каркас. Нижние отступы прокручиваемого отдельного экрана задаются с учётом `useSafeAreaInsets().bottom`; внутри вкладок нижней safe area владеет таб-бар. `bodyStyle` каркаса позволяет задать общий контейнер вкладок. Конкретные размеры детальных экранов сохраняются в их стилях.

Декоративная полоса включается параметром `stripe`, сетка — `grid`. По умолчанию оба включены. Разница отступов между макетами допустима; не вводить одинаковый padding везде ради единообразия.

Полоса закреплена отдельным абсолютным слоем у верхнего края. Её положение не управляет safe area содержимого: `safeTop` по умолчанию включён. Каркас отступает от верхней системной области, а при нулевом inset — как минимум на высоту полосы. Боковые safe area учитываются для поворота устройства. Не отключайте `safeTop`, чтобы передвинуть декор: это разрешает содержимому попадать под статус-бар.

## Добавить поле товара

Категория задаётся явно в `Product.category`: `technology` («Техника») или `leisure` («Для отдыха»). Кнопка «Все» показывает обе категории. Совместная фильтрация по категории и названию находится в `features/catalog/model/catalog-filter.ts`. Поиск применяется при вводе; поиск и категории закрепляются через заголовок секции `SectionList` в экране каталога. При добавлении категории обновить тип товара, список кнопок и демоданные.

1. Обновить `entities/product/model/product.ts`.
2. Обновить демоданные в `entities/product/mocks/products.ts`.
3. Обновить преобразование DTO, когда появится реальный контракт API.
4. Если поле важно для уже согласованной аренды, проверить `snapshotProduct` и тест независимости снимка от каталога.
5. Отобразить поле в нужных компонентах. В UI не импортировать массив демотоваров напрямую.

`pricePerHour` — рубли за час; итоговая стоимость записывается в сессию при старте. Для реальной оплаты сервер должен выдать котировку и явно определить денежные единицы. `photo` поддерживает локальный числовой ресурс и объект `{ uri }`. Проверку удалённых URL выполняет будущий адаптер.

## Добавить запрос

Общая настройка транспорта находится в `shared/api`. Конкретные операции — в `entities/product/api` или `features/rentals/api`. Транспортный тип не является проверкой ответа: адаптер проверяет DTO во время выполнения и переводит его в доменную модель.

`ProductRepository` предоставляет асинхронные `list` и `find`. Сейчас провайдер получает начальное демонаполнение и затем загружает список. Будущий адаптер пагинации и отдельной загрузки товара нужно реализовать по серверному контракту; текущий провайдер рассчитан на полный небольшой каталог.

`RentalService` описывает проверку доступности, оплату и открытие ячейки. Источник выбирается в `AppProviders`. Сейчас подключён `createDemoRentalService`. Для реального сервиса реализовать тот же интерфейс, уточнить серверные параметры и заменить подключение. Не включать реальную интеграцию через фиктивный URL.

## Добавить этап аренды

1. Обновить тип состояния и события в `model/rental-session.ts`.
2. Описать разрешённые переходы и ограничения; добавить тесты до подключения UI.
3. Добавить компонент в `components/stages`, подключить его в `RentalStageView`.
4. Обновить заголовки в `model/stage-content.ts`, подпись в списке аренд.
5. Добавить обработчик контроллера и при необходимости операцию сервиса.
6. Обновить таблицу `docs/rental-state.md` и изолированный демосценарий.

Представление вызывает обработчики из props. Оно не меняет глобальное состояние и не выполняет запросы. Локальные модалки и выбор способа оплаты остаются состоянием UI; реальный способ оплаты пока не интегрирован в платёжную систему.

## Найти неисправность

- Неверная сумма / этап → проверить reducer, снимок товара и события.
- Операция зависает / завершилась не вовремя → проверить `useRentalOperation`, отмену сигнала и revision.
- Не открывается URL → проверить параметры, productId и необязательный query `rentalId`.
- Неверный отступ → проверить владельца safe area и отсутствие второго `ScreenFrame`.
- Текст обрезается → проверить стиль конкретного компонента и измерение шрифта в `display-text-width.ts`; не удалять его без проверки web и устройства.
- Для воспроизведения ошибки этапа открыть «ДЕМО» в development-сборке: это отдельная сессия предпросмотра, рабочая аренда продолжает жить независимо.

`AppError` различает ошибки конфигурации, транспорта, HTTP, операций и рендера. В UI показывается безопасный текст и повторная попытка. Граница ошибок рендера перезапускает дерево провайдеров: локальные демосессии при таком восстановлении сбрасываются. Это ограничение прототипа, не механизм восстановления серверной аренды.

Логи разработки содержат только разрешённые технические поля: событие, этапы, категорию и имя операции. Не добавлять туда тело запроса, заголовки, платёжные данные и свободный текст обращения.

## Проверки

```sh
npm run check
```

Команда запускает TypeScript, ESLint, node:test и проверку циклов. Тесты `*.test.cjs` располагаются рядом с моделью и сервисом; runner использует уже установленный TypeScript для загрузки чистых TS-модулей. Новых тестовых зависимостей нет.

GitHub Actions описан в `.github/workflows/check.yml`: Node 24, npm ci, npm run check. Удалённый запуск произойдёт после публикации изменений; локальное наличие workflow не доказывает успешный CI.

Проверка Expo после изменений маршрутов:

```sh
npx expo export --platform web --output-dir .expo/refactor-web
npx expo export --platform android --output-dir .expo/refactor-android
```

Экспорт Android не равен запуску на телефоне. Результаты ручной проверки записаны в `docs/refactoring-validation.md`.


## Пункты выдачи

`entities/pickup-point` содержит модель, заменяемый `PickupPointRepository`, провайдер и демоданные. Источник подключается в `AppProviders`. Адреса и расписание демонстрационные.
`features/points` отображает список и поиск по названию/адресу. Кнопка открывает каталог с query-параметром `point`; неизвестный или недоступный пункт получает отдельное состояние. «Все пункты» снимает фильтр, «Сменить пункт» возвращает к списку.
Товары связаны через `Product.pickupPointId`. Поле `pickupPoint` хранит название/адрес для отображения и снимка аренды: изменение выбранного фильтра не меняет начатую аренду. При интеграции API адаптер должен заполнять оба поля из согласованных данных пункта. В демоданных вещи распределены между университетом и библиотекой.
