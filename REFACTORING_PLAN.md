## 1. Задача для агента

Провести поэтапный рефакторинг Expo / React Native приложения, сохранив работающие пользовательские сценарии и текущий дизайн. Сделать код понятным для владельца проекта: легко находить источник ошибки, менять отдельный экран и добавлять функциональность без правок во всём приложении.

Это рефакторинг существующего приложения. Подключение реальной оплаты, серверного бронирования, управления замками, отправки обращений и создание новых продуктовых сценариев не входят в задачу. Подготовить для них понятные точки подключения.

Перед началом прочитать `AGENTS.md`, проверить актуальные файлы и незакоммиченные изменения. Этот документ описывает состояние на дату подготовки: если код изменился, скорректировать последовательность и записать причину. Не откатывать и не перезаписывать изменения пользователя.

## 2. Исходное состояние и проблемы

На момент подготовки используется Expo `~58.0.19`. Фактические версии всегда читать из `package.json`. Маршруты находятся в `src/app/`, экраны — в `src/features/`.

Основные точки рефакторинга:

| Текущий файл / область | Что требуется исправить |
| --- | --- |
| `src/features/rentals/screens/rental-flow-screen.tsx` | Разметка всех этапов, эффекты, таймеры, переходы и демосценарии находятся вместе. |
| `src/features/rentals/state/rental-session.tsx` | Произвольный `update` с `patch` позволяет менять этап без проверки допустимости перехода. Здесь же находятся форматирование и таймер. |
| Провайдер и экран аренды | Проверка истечения брони дублируется. |
| `src/features/home/data/catalog-products.ts` | Тестовые данные и тип товара используются арендой напрямую из модуля главного экрана. |
| `src/features/home/types/item.ts`, `api/items-api.ts`, `hooks/use-items.ts` | Заготовка API использует другую модель товара, чем работающий каталог. Проверить реальное использование перед заменой или удалением. |
| `src/features/rentals/components/rental-presentation.tsx` | В одном файле собраны разные компоненты оформления. Разделять по ответственности и реальному использованию. |
| `src/components`, `src/constants`, `src/hooks` | Общие компоненты, тема, навигация и остатки шаблона смешаны. |

Сейчас аренда — локальный демосценарий. Сессии хранятся в памяти, ответы API имитируются задержками, после перезапуска данные сбрасываются. Это не подтверждение реальной оплаты или выдачи.

## 3. Целевая архитектура

Модульная архитектура по функциональности с небольшим общим слоем сущностей. Не вводить все слои полноценной FSD или Clean Architecture ради структуры папок.

```text
src/
├── app/                         # Только маршруты Expo Router и layouts
├── core/
│   ├── providers/               # Подключение общих провайдеров
│   └── navigation/              # Таб-меню, сборка навигации
├── entities/
│   └── product/
│       ├── model/               # Product и статусы
│       ├── api/                 # Получение товаров, DTO → Product
│       ├── mocks/               # Тестовые товары и реализация источника
│       └── index.ts             # Публичные экспорты
├── features/
│   ├── catalog/                 # Каталог и карточка выбранного товара
│   ├── rentals/                 # Оформление, получение, список аренд
│   ├── points/                  # Пункты выдачи
│   └── profile/                 # Профиль и настройки
└── shared/
    ├── ui/                      # Кнопки, текст, поля, бейджи
    ├── layout/                  # Контейнеры экранов, фон-сетка, полоса
    ├── theme/                   # Цвета, типографика, отступы, тема
    ├── api/                     # HTTP-клиент и общие ошибки запросов
    ├── hooks/                   # Только универсальные хуки
    ├── lib/                     # Универсальные небольшие функции
    ├── config/                  # Проверенные настройки окружения
    └── diagnostics/             # Логи и обработка ошибок
```

Папки создавать при появлении содержимого. `assets/` оставить в корне, не переносить шрифты и изображения без необходимости.

Внутри модуля аренды:

```text
features/rentals/
├── screens/                     # Сборка экранов и подключение навигации
├── components/
│   └── stages/                  # Представления отдельных этапов
├── hooks/                       # Связь сценария с интерфейсом
├── model/                       # Типы, события, reducer, селекторы, расчёты
├── api/                         # Операции сервиса аренды
├── mocks/                       # Демо-реализация этих операций
├── dev/                         # Переключение демосценариев
└── index.ts                     # Публичный интерфейс модуля
```

### Направление зависимостей

- `app` и `core` собирают приложение из модулей.
- `features` могут использовать `entities` и `shared`.
- `entities` могут использовать `shared`, но не `features`.
- `shared` не импортирует ничего из `features`, `entities`, `core` или `app`.
- Каталог и аренда получают товар через `entities/product`, а не через внутренние файлы друг друга.
- Внешние потребители модуля используют его `index.ts`. Внутри модуля использовать прямые относительные импорты, чтобы избежать циклов через собственный `index.ts`.
- Чистая модель аренды не зависит от React, навигации, HTTP и UI.

### Правила размещения кода

- Общая кнопка, поле, текст → `shared/ui`.
- Блок комплекта, таймер брони, карточка оформления → `features/rentals/components`.
- Тип и источник товаров → `entities/product`.
- Общий HTTP-клиент → `shared/api`; конкретная операция аренды → `features/rentals/api`.
- Хук нужен только аренде → `features/rentals/hooks`; универсальный → `shared/hooks`.
- Расчёт стоимости и проверка перехода → `features/rentals/model`.
- Маленький `StyleSheet` оставлять в компоненте; большой выносить в соседний `*.styles.ts`. Общие значения брать из темы.
- Тесты хранить рядом с проверяемой логикой или в локальном `__tests__` соответствующего модуля.
- Открытие модалки, ввод текста и выбор вкладки не переносить в глобальное состояние без необходимости.

## 4. Ограничения реализации

1. Сохранить дизайн, шрифт Lozung, светлую и тёмную темы, сетку, SVG-иконки, декоративную полосу, безопасные отступы и четыре вкладки.
2. Сохранить существующие публичные маршруты: `/`, `/points`, `/rental`, `/profile`, `/product/[id]`, `/checkout/[id]`, `/rental-flow/[id]`. Не менять смысл существующего параметра `id` незаметно для вызывающего кода.
3. Сохранить публичные UUID товаров и независимые отображаемые коды. Отображаемый код — элемент дизайна, не средство авторизации.
4. Сначала делать механические переносы и обновление импортов, затем менять ответственность и логику. Не смешивать массовое форматирование с функциональными изменениями.
5. Не добавлять Redux, Zustand, библиотеку машин состояний или DI-контейнер без конкретной необходимости. Для текущего масштаба начать с типизированного reducer, Context и обычных функций.
6. Новые зависимости обосновать; устанавливать по правилам `AGENTS.md`. Не обновлять SDK и прочие пакеты попутно.
7. Учесть Android, iOS и web. Успешная проверка web не означает проверку нативного приложения.
8. Не заменять нынешние обходы проблем шрифта, размеров текста, SVG и safe area без воспроизведения и проверки результата.
9. Отдельно документировать обнаруженные продуктовые ошибки. Исправления, меняющие правила оплаты или брони, не маскировать под перенос файлов.

## 6. Проверочные сценарии

### Автоматические проверки логики

- Доступный и занятый товар дают правильные результаты проверки.
- Стоимость для 1 часа, 3 часов и суток сохраняет действующие правила.
- Запрещённый переход не меняет сессию.
- Истечение срока обрабатывается на границе времени и после возвращения из фона.
- Устаревший ответ не возвращает истёкшую бронь к оплате или получению.
- Двойное нажатие не создаёт повторную операцию.
- Подтверждение получения недоступно без полного комплекта.
- Возврат из проблемы ведёт в корректный этап и не обходит ограничения.
- Новая аренда того же товара не перезаписывает другую сессию.
- Неизвестный товар, отсутствующая сессия и неверные параметры маршрута обрабатываются явно.

### Ручная и интеграционная проверка

- Каталог → товар → оформление; цена и срок передаются корректно.
- Без согласия на условия новая аренда не запускается.
- Проверка → оплата → получение → комплект → активная аренда.
- Ошибка оплаты, повторная попытка и истечение брони.
- Ошибка открытия ячейки, повторная попытка и форма проблемы.
- Подготовка обращения остаётся явно обозначенной демооперацией без отправки.
- Выход из сценария и продолжение через список аренд.
- Прямой переход по URL без сессии показывает понятный экран.
- Все четыре вкладки и возврат назад работают без предупреждений маршрутизатора.
- Светлая / тёмная тема; узкий экран около 320 px и обычный мобильный экран.
- Названия карточек ограничены двумя строками, цены в ряду выровнены снизу.
- Изображения вписываются в контейнер; подписи кнопок и таймер не обрезаются.
- Полоса, сетка, клавиатура и safe area не перекрывают содержимое.

Проверить доступные платформы и честно записать непроверенные. Для каждого этапа выполнить:

```bash
npx tsc --noEmit
npx expo lint
```

Дополнительно запускать релевантные тесты; после существенных изменений маршрутизации или конфигурации проверять сборку / экспорт подходящей платформы. Если появится `bun.lock`, использовать команды по актуальному `AGENTS.md`.

## 7. Порядок сдачи работы

Выполнять этапы последовательно, сохраняя запускаемое приложение после каждого. Тесты на критическую логику добавлять до или вместе с её изменением, а не только в конце.

После каждого этапа обновлять чекбоксы и краткий журнал ниже: что сделано, какие проверки прошли, что осталось и какие решения приняты. Не отмечать визуальную или нативную проверку выполненной, если она фактически не проводилась.

В итоговом отчёте указать:

1. Новую структуру и основные точки входа.
2. Какие обязанности перенесены и какие проблемы устранены.
3. Результаты проверок и доступные платформы.
4. Оставшиеся ограничения деморежима и отдельные задачи подключения сервера.
5. Как добавить новый этап аренды, экран или поле товара.
